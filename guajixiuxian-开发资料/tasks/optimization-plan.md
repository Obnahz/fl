# 优化计划：修炼数值契约

## 总目标

只优化当前核心循环，不新增系统。统一手动修炼、自动修炼与闭关至圆满的成本、收益、倍率和任务计数，让玩家能预测、理解并复盘每次操作。

## 关键问题

当前三条修炼路径没有共用同一套结算契约：UI 预估、Worker 计算和 Store 应用倍率存在分歧。这样会造成预估成本与实际扣除不一致、批量修炼收益异常，以及宗门方向的价值无法被玩家正确理解。

## 架构决策

- `playerStore.cultivate()` 作为应用有效修炼倍率的唯一入口。
- Worker 只负责批次数量、随机判定和成本规划，不重复应用倍率。
- UI 预估、实际结算和失败提示复用同一个纯计算函数。
- 本阶段不改突破失败损失、历练危险率、战斗公式和主要资源产出。

## 阶段 1：统一计算

### Task 1：建立批量修炼纯计算器

**目标**：在规则插件中增加无 UI 的纯计算函数，返回批次数、总成本、原始收益和最终收益。

**验收标准**
- 同一等级、灵根、宗门方向和随机种子下，结果可重复。
- 灵根和宗门倍率各只应用一次。
- 能处理灵力刚好足够和差 1 点的边界。

**验证**
- 增加等级 1、10、19 的固定输入测试。
- 覆盖无加成、灵根加成、灵根加宗门加成。

**依赖**：无

**可能涉及文件**：`src/plugins/gameRules.js`、`src/workers/cultivation.js`、`tests/game-rules.test.js`

### Task 2：统一三种修炼入口

**目标**：让手动、自动、闭关使用相同的单位收益和成本规则，保留现有任务事件与存档行为。

**验收标准**
- 相同输入下三种路径的单位收益规则一致。
- 闭关按钮的预估成本与实际扣除完全一致。
- 批量操作对每日任务的计数语义明确，并在三处保持一致。

**验证**
- 增加 Store 层集成测试，覆盖灵根、宗门静修和灵力不足。
- 现有 101 项规则测试全部通过。

**依赖**：Task 1

**可能涉及文件**：`src/stores/player.js`、`src/views/Cultivation.vue`、`src/workers/cultivation.js`

### 检查点：计算契约

- 三种路径通过相同固定输入对照。
- 完整 `node --test` 测试集通过。
- Vite 生产构建通过。

## 阶段 2：反馈与可读性

### Task 3：统一修炼反馈

**目标**：让玩家在操作前看到预计成本和收益，结算后看到实际结果和倍率来源。

**验收标准**
- 操作前显示预计消耗、预计获得和预计剩余灵力。
- 操作后显示实际消耗、实际获得和突破状态。
- 失败时显示缺少的灵力或具体失败原因。

**验证**
- 桌面端与 320px 宽度检查文本不重叠。
- 手动、自动、闭关各完成一次并核对日志。

**依赖**：Task 2

**可能涉及文件**：`src/views/Cultivation.vue`、`src/components/LogPanel.vue`

### Task 4：增加轻量观察指标

**目标**：只记录本轮试玩需要的指标，不改变存档结构和游戏数值。

**验收标准**
- 记录三种修炼路径的使用次数、平均批次收益和失败原因。
- 记录首次修炼、首次突破和首次切换方向时间。
- 退出和重新进入不会重复计数。

**验证**
- 新存档完成 30 秒试玩并导出记录。

**依赖**：Task 2

**可能涉及文件**：`src/stores/player.js`、`src/views/Cultivation.vue`、`src/plugins/log.js`

### 检查点：玩家可读性

- 新玩家在 10 秒内能说出当前目标、成本和下一步。
- 玩家能解释实际结果为什么与预估一致。
- 反馈不会遮挡任务、洞府和突破入口。

## 阶段 3：回归与调优

### Task 5：固定种子数值快照

覆盖等级 1、10、19；无加成、灵根加成、灵根加宗门加成；灵力刚好足够和差 1 点。

**依赖**：Task 1、Task 2

### Task 6：30 秒真实试玩审计

**验收标准**
- 新存档完成创建、第一次修炼和第一次明确的下一步选择。
- 旧存档回归后离线收益、任务和宗门状态不丢失。
- 玩家能用一句具体的话复盘等待或失败原因。

**验证**
- 桌面端与移动端各走一遍。
- 记录首次困惑点、首次无聊操作和下一局想尝试的路径。

**依赖**：Task 3、Task 4、Task 5

## 完成标准

- 三种修炼路径数值一致且可解释。
- 既有测试与构建全部通过。
- 试玩没有出现“预估与结算不一致”或“下一步不明确”。
- 在以上检查点通过前，不新增系统或奖励池。

## 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 修正后改变老玩家突破速度 | 高 | 先做旧结果快照，必要时只修正未来批次 |
| 批量操作改变每日任务节奏 | 中 | 先确定按批次或实际次数计数，再同步文案与测试 |
| Worker 与 Store 重复改状态 | 高 | 先落纯计算器，再改调用方，最后删除重复倍率 |
